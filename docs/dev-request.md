# Запит до адміна / розробника поточного сайту

**Контекст:** робимо новий фронтенд для вже працюючого сайту на **WordPress + WooCommerce**, оплати — **WayForPay**. У базі вже є покупці й видані доступи до відео. Підхід — **гібрид**: новий фронт = лендинг/сольники/трейлери, а кошик/оплата/кабінет/перегляд відео лишаються в WooCommerce. **WordPress = єдине джерело правди, міграції БД НЕ робимо** (саме міграція = головний ризик зламати доступи й паролі).

Позначки: **[адмін]** — доступи/акаунти, **[dev]** — технічні відповіді.

---

## ⚡ Мінімум, щоб стартувати швидко (гібрид-MVP)

Цього достатньо, щоб уже перевести кнопки нового фронту в реальний магазин і протестувати покупку:

1. **[dev]** Для кожного сольника — **ID товару WooCommerce + SKU + ціна + посилання (permalink)**.
2. **[dev]** URL-патерни: **add-to-cart**, **cart**, **checkout**, **my-account** (і сторінка, де покупець дивиться куплені відео).
3. **[адмін]** Рішення по домену (див. розділ F) + доступ до **DNS / хостингу**.
4. **[адмін]** **Staging-середовище** або копія БД — щоб тестувати, не чіпаючи прод.
5. **[dev]** Підтвердити, що **WayForPay + видача доступу** працюють без змін (ми їх не торкаємось).

---

## Повний список для фіналізації бекенду

### A. Доступи
- **[адмін]** Доступ до **адмінки WordPress** (або окремий акаунт) — спершу для огляду.
- **[адмін]** **Staging** + свіжа **копія БД** (або read-only експорт) для тестів.
- **[адмін]** Доступ до **хостингу/SFTP** (або через dev) — знати провайдера, налаштувати проксі/розмістити файли.
- **[адмін]** Доступ до **DNS** (реєстратор домену) — для маршрутизації та cutover.
- **[dev]** **WooCommerce REST API ключі** (consumer key/secret) — спершу read, пізніше read/write.

### B. WooCommerce / каталог
- **[dev]** Версії: **WordPress / WooCommerce / PHP**.
- **[dev]** **Список активних плагінів + тема** (особливо: WayForPay, членство/доступ до відео, LMS, кешування, security/WAF — вони можуть блокувати REST/CORS).
- **[dev]** Тип товарів-сольників: simple / variable / **downloadable / virtual** / subscriptions?
- **[dev]** Точні URL: `?add-to-cart=ID`, cart, checkout, **my-account**.

### C. 🔑 Доступ до відео — НАЙКРИТИЧНІШЕ (від цього залежить уся «бібліотека»)
- **[dev]** Яким **механізмом** видається доступ після оплати? (WooCommerce **Memberships** / **Subscriptions** / «downloadable products» / LMS — LearnDash/Sensei/Tutor / Restrict Content / кастомний user-meta?)
- **[dev]** **Де хостяться відео** і як захищені: приватне **Vimeo** / **Bunny.net** / самохост / unlisted YouTube / DRM? Як контролюється відтворення (підписані URL, перевірка членства, oEmbed-гейтинг)?
- **[dev]** **Модель даних:** як саме зберігається «користувач X має доступ до сольника Y» (таблиця / post-meta / user-meta / membership plan → product)?
- **[dev]** Чи є **готовий ендпоінт**, щоб прочитати доступи користувача? Якщо ні — чи може dev додати **кастомний REST-ендпоінт**: авторизований користувач → список його сольників (+ короткоживучий підписаний URL відтворення на кожен)?

### D. Авторизація / користувачі
- **[dev]** Як зараз **логіняться покупці** (email/пароль WooCommerce? соцмережі?).
- **[dev]** Чим вмикаємо вхід із нового фронту: **JWT Authentication for WP REST API** (для headless) / cookie-сесія (якщо один домен) / редірект на WP-логін? Що dev може ввімкнути?
- **[обидва]** Письмово підтвердити: **WordPress = джерело правди, БД НЕ мігруємо** (щоб ніхто «не допоміг» експортом-міграцією — паролі phpass усе одно не переносяться).
- **[dev]** Орієнтовна **кількість покупців** і структура (для розуміння, не для міграції).

### E. Платежі / WayForPay
- **[dev]** Який саме **інтеграційний плагін WayForPay** (офіційний для WooCommerce чи кастом?) + версія.
- **[dev]** Потік оплати: **redirect** (Woo → платіжна сторінка WayForPay → callback) чи є API-ініціація?
- **[dev]** Конфіг **serviceUrl** (S2S callback) і **returnUrl** — підтвердити, що **callback лишається на Woo** (тоді доступ видається без змін); чи можна задати **власний returnUrl** на наш екран успіху.
- **[dev]** **Тестові (sandbox) дані WayForPay** для покупки на staging (або тест-товар на малу суму).
- **[dev]** Обробка **скасування/невдалої оплати** (щоб наш флоу збігався).

### F. Домен / хостинг / інфраструктура
- **[адмін/dev]** **Рішення по домену:**
  - *Рекомендовано* — **один домен**: корінь = новий фронт, а `/shop`, `/cart`, `/my-account` → WooCommerce (reverse-proxy/субдиректорія). Сесія, кошик і логін безшовні.
  - *Альтернатива* — **піддомен** `shop.shatailo.com` = Woo. Простіше, але перехід помітний, окремі cookie.
- **[dev]** **CORS** для `/wp-json/...` (якщо фронт на іншому origin) + чи не блокує REST якийсь **security-плагін / WAF**.
- **[dev]** **Кеш/CDN** (Cloudflare, WP Rocket): персональні сторінки (кошик/акаунт/API) мають **обходити кеш**.

### G. Дрібне
- **[адмін]** Email для контакт-форми (зараз mailto-фолбек; підключимо Web3Forms/SMTP).
- **[адмін]** Існуючі **аналітика/пікселі**, які треба зберегти.

---

## 🔒 Безпека (важливо)
- **Секрети не виходять у фронтенд.** WayForPay `merchantSecretKey` і будь-які **write**-API-ключі лишаються **на сервері (WP)**. Статичний сайт їх не містить.
- Усі тести — **тільки на staging** з копією БД.
- Не пишемо напряму в `wp_users` / таблиці замовлень — лише через офіційні API/механізми Woo.

---

## Порядок дій після відповідей
1. Підняти staging, увімкнути REST/JWT, видати API-ключі.
2. **Тест-покупка наскрізь** на staging: WayForPay → callback → доступ видано.
3. Перевірити, що **існуючий старий покупець** теж бачить свої відео (нічого не зламалось).
4. Перевести кнопки нового фронту в реальний Woo → cutover за планом + готовий rollback.
